# 通用日誌分析工作流程規範 (Universal Log-Driven Analysis Workflow)

本規範為所有工程專案（硬體通訊、軟體除錯、系統架構）之永久強制執行標準。日誌（LOG）是現場除錯的唯一客觀依據，嚴禁在未分析真實日誌前憑空猜測。

---

## 1. 核心原則：日誌優先原則 (Log-First Principle)

當使用者回報「測試有問題」、「數據不對」、「無法連線」或提到「已將結果記錄在 LOG」時：
* **第一優先動作**：必須立即主動搜尋並讀取最新的 `.log` 檔案。
* **嚴格禁止**：在未讀取並分析真實日誌數據前，向使用者提出未經佐證的假設或要求使用者進行盲目操作。

---

## 2. 標準四步日誌診斷流程 (4-Step Log Diagnosis Pipeline)

每次進行問題排查時，必須嚴格依序執行以下 4 步流程：

### 步驟 1：定位最新日誌 (Locate)
* 自動搜尋專案目錄、`logs/` 與 `Release/` 下最近 30 分鐘內產生的所有 `.log` 檔案。
* 確認日誌時間戳記與使用者測試時間精確吻合。

### 步驟 2：提取關鍵證據 (Extract)
* 提取設備前綴標籤（如 `[WT333E]`, `[KEB_DRIVE]`, `[TORQUE]`, `[GL820]`, `[SYSTEM]`）。
* 提取**原始二進位電文 (`HEX [...]`)**、**ASCII 回傳字串**、**狀態代碼 (如 Ack 碼)** 與 **Win32/CLR 例外堆疊**。

### 步驟 3：原廠規範交叉比對 (Cross-Reference)
* 將日誌中抓出的 Raw Bytes / Status Code 與本機儲存的原廠備份（如 `Vendor_Softwares_Backup/`、手冊 PDF、Legacy 源碼如 `.bas`/`.c`）進行二進位記憶體結構、波特率常數、Service 代碼的比對。
* 找出底層失敗的根本原因。

### 步驟 4：透明證據回報 (Transparent Report)
* 向使用者回報時，**必須先完整引用日誌中的原始紀錄（Verbatim Log Excerpt）**。
* 逐行向使用者解說該行日誌代表的硬體/通訊狀態，並列出修復後的確切技術依據。

### 步驟 5：用畢即清強制清理 (Auto-Purge & Teardown)
* **不可違背之鐵律**：在輸出分析報告之前，**必須強制調用刪除指令，將 `logs/*` 下所有已分析完畢的 `.log`、`.csv` 及所有臨時截圖 `.jpg`/`.png` 全數清除**。
* 確保測試與發布目錄永遠處於乾淨純粹的「零垃圾日誌」狀態，嚴禁留給使用者手動刪除或提醒。

---

## 3. 日誌衛生規範 (Log Hygiene)
* **時間戳記**：日誌每行必須具備 `[yyyy-MM-dd HH:mm:ss.fff]` 毫秒級時間戳。
* **分級標籤**：明確標記 `[OK]`, `[FAIL]`, `[HEX]`, `[EXCEPTION]`, `[DIAG]`。
* **檔案清理**：分析結束立即自動銷毀臨時日誌與截圖，嚴格落實用畢即清。
