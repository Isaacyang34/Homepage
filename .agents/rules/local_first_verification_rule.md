# GitHub 發布授權與地端優先驗證規範 (Local-First Verification & Explicit Release Authorization)

## 1. 核心意圖與原則
* **杜絕未成熟的遠端推送**：在複雜軟體（包含 GUI 介面、即時通訊、演算法計算與資料庫操作）中，很多功能必須在地端作業系統環境真實跑過，才能確保沒有任何邊界缺陷或視覺瑕疵。
* **節省 Token 與網路資源**：每一次推送遠端涉及打包、雜湊運算、雙分支同動以及網址確認，未確認穩定前頻繁推送到 GitHub 既危險又浪費 Token。
* **明確授權門檻**：除非使用者發出明確文字指令（例如「請發布到 GitHub」、「推送到遠端」、「發布 release」），否則所有工作一律限於本地端閉環完成。

## 2. 嚴格執行規範
1. **未經指示嚴禁調用 `git push`**：
   - 任何改動僅限於本地修改、單元測試、編譯與便攜打包（例如產出本地 `Stock_Portfolio_Tracker.exe`）。
   - 嚴格禁止在沒有使用者指令授權的情況下擅自發起 `git push origin ...`。
2. **回報聚焦本地驗證**：
   - 完成修改後，直接提供本機檔案路徑（如 `c:\...\Stock_Portfolio_Tracker.exe` 或啟動腳本）。
   - 請使用者在地端雙擊啟動、親自操作確認是否滿意。
3. **正式發布觸發點**：
   - 當使用者確認功能完全無誤，並**明確給予「發布到 GitHub」指示**後，才依照第 7 條鐵律執行雙分支同動推送（`gh-pages` 與 `master`）。
